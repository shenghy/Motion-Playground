# 透明视频导出性能优化设计

## 背景

Overlay Studio 当前把每个 1920×1080 透明画面先通过 `html-to-image` 生成 PNG，再逐帧上传给本地服务，由 FFmpeg 编码为 30fps ProRes 4444 MOV。现有实现能够保证确定性、透明通道和帧顺序，但每一帧都会等待两次浏览器重绘、重新遍历并克隆导出 DOM、重新分析字体资源、压缩 PNG，并等待一次独立 HTTP 请求完成。

本机单独编码基准显示，FFmpeg 对 300 帧静态透明素材的处理速度约为 47.6fps；浏览器侧仅两次 `requestAnimationFrame` 就产生约 33ms/帧的理论等待。因此本轮优先优化浏览器采帧链路，不改变输出规格。

## 目标

- 保持 MOV 输出为 1920×1080、30fps、ProRes 4444、有效 Alpha 通道。
- 保持当前确定性时间采样、项目快照、取消、重试和旧任务失效行为。
- 去除每帧重复执行的字体准备和字体 CSS 分析。
- 把每帧两次绘制等待缩减为一次，同时通过回归测试保证 React 内容和 CSS 动画时间已经提交。
- 记录准备画面、PNG 捕获、上传等待、最终编码和保存阶段耗时，让界面能够显示实际速度和预计剩余时间。
- 使用固定导出夹具做修改前后对比；目标是在当前机器上将浏览器采帧总耗时至少降低 25%，并报告真实结果，不以目标替代验收。

## 不在本轮范围

- 不降低分辨率、帧率或透明通道质量。
- 不把 ProRes 4444 换成 H.264、HEVC 或不带 Alpha 的硬件编码格式。
- 不重写现有 React 动效组件为 Canvas/WebGL。
- 不立即引入 Playwright/无头 Chromium 导出服务。
- 不贸然并行捕获多个 DOM 帧；共享 React 舞台的时间状态不适合并发修改。

## 方案比较

### 方案 A：优化现有浏览器采帧链路（本轮采用）

保留当前架构，缓存 `html-to-image` 所需的字体嵌入 CSS，把字体就绪等待提升到导出会话初始化阶段，使用同步 React 提交配合一次绘制等待，并增加阶段计时。

优点是改动集中、输出兼容性风险最低，现有取消和本地 FFmpeg 服务可以继续使用。缺点是仍需逐帧克隆 DOM 和压缩 PNG，速度上限仍低于原生渲染管线。

### 方案 B：单请求流式传输 PNG

浏览器用一个带长度前缀的请求持续传输 PNG，服务端解析后写入 FFmpeg，消除每帧 HTTP 往返。

它能减少本地协议开销，但不能解决 DOM 克隆和 PNG 压缩这一主要瓶颈，而且浏览器流式请求的错误、取消与兼容处理更复杂。只有阶段计时证明上传等待占比明显时，才进入后续优化。

### 方案 C：专用无头浏览器或 Canvas 原始帧

由服务端控制 Chromium 截图，或把组件改造成 Canvas/OffscreenCanvas 后直接向 FFmpeg 传 RGBA。

它的长期性能潜力最大，但前者需要新增导出页面和进程协调，后者接近重写渲染层。本轮不采用。

## 架构设计

### 导出捕获会话

`ExportSurface` 增加明确的会话生命周期：

1. `beginCaptureSession()` 等待字体就绪，并调用 `getFontEmbedCSS()` 生成一次可复用的字体 CSS。
2. `prepareFrame(time)` 同步提交指定导出时间，设置该帧下所有 CSS 动画的 `currentTime`，等待一次浏览器绘制边界。
3. `capturePng()` 调用 `toBlob()`，传入会话缓存的 `fontEmbedCSS`，不再逐帧扫描样式表和字体资源。
4. `endCaptureSession()` 清理缓存；项目变化或取消后不得把旧会话资源带入下一次导出。

PNG 序列和 MOV 共用同一捕获会话，避免两条路径出现不同画面。

### 性能计时

计时使用单调时钟，并按以下阶段累计：

- `preparing`：字体准备和会话初始化。
- `framePrepare`：提交 React 状态、校准动画和等待绘制。
- `frameCapture`：DOM 克隆、SVG/Canvas 转换及 PNG 压缩。
- `frameTransfer`：MOV 路径上传到本地服务并等待接收。
- `encoding`：结束输入到 FFmpeg 退出。
- `saving`：把完成的 MOV 流写入用户选择的文件。

进度模型继续保留已完成帧数，同时增加实时平均帧速率、已用时间和预计剩余时间。预计剩余时间只在至少完成一帧后显示，取消和错误状态不显示误导性的 ETA。

### FFmpeg 服务

本轮保留逐帧 PUT 和现有背压控制。服务端增加编码阶段耗时返回值，供浏览器合并到性能摘要。编码参数保持 `prores_ks`、profile 4 和 Alpha 像素格式，不通过降低质量换速度。

## 正确性与错误处理

- 会话初始化失败时不创建或继续 MOV 任务。
- 任意帧失败时沿用现有任务清理逻辑，并确保捕获会话在 `finally` 中结束。
- 取消必须能打断帧循环和保存，不允许因新增计时阻塞取消按钮。
- 字体缓存只在单次不可变项目快照内复用。
- 若一次绘制等待导致画面未提交或动画时间错误，回归测试必须失败；实现应修复提交顺序，而不是静默恢复到无条件双等待。

## 测试与验收

### 自动化测试

- `ExportSurface`：字体 CSS 每个会话只计算一次；每帧 `toBlob` 都收到缓存；结束会话后重新计算。
- `ExportSurface`：准备帧只经过一次绘制边界，且捕获到新时间对应的卡片和动画时间。
- MOV/PNG 控制器：正常完成、取消和异常都会结束捕获会话。
- 性能统计：阶段累加、帧速率和 ETA 在零帧、单帧及多帧情况下正确。
- 服务端：完成响应包含编码耗时，原有帧校验和任务生命周期不变。

### 完整验证

- 运行全部 Vitest、lint 和生产构建。
- 运行真实 FFmpeg 集成测试，使用 `ffprobe` 验证 ProRes 4444、Alpha 像素格式、1920×1080 和 30fps。
- 使用同一个固定 10 秒导出夹具分别记录优化前基线和优化后耗时，至少执行三次，比较中位数。
- 检查生成 MOV 的首帧、中间帧和末帧 Alpha，不只检查文件元数据。

## 后续决策门槛

如果浏览器采帧耗时下降不足 25%，或 `frameTransfer` 占总耗时超过 15%，下一阶段优先实施单请求流式传输；如果 `frameCapture` 仍占总耗时 70% 以上，则评估专用无头 Chromium 导出页面。后续架构升级必须以本轮计时数据为依据。
